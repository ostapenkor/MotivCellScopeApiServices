# MotivCellScope — требования к интерфейсу (анализ макетов дизайнера)

Документ составлен по итогам разбора дизайнерских файлов (`login.html`,
`dashboard.html`, `incidents.html`, `monitoring.html`, `reports.html`,
`admin.html`, `script.js`, `style.css`) и сверки с фактическими возможностями
REST API (см. `API_DOCUMENTATION.md`).

Статусы в таблицах:

- **Есть в макете** — элемент нарисован и его можно оставлять;
- **Доработать** — элемент есть, но в текущем виде не соответствует API, ролям или данным;
- **Нет в макете** — элемент нужен, дизайнеру его ещё предстоит сверстать;
- **Нет API** — элемент нарисован, но бэкенд данных/операций для него не предоставляет.

---

## 0. Главное резюме

Дизайнер сверстал **визуальную оболочку** (тёмная тема, шапка с вкладками,
карточки, таблицы, бейджи), но не спроектировал само приложение:

1. Все данные во всех страницах — статичный HTML, ни одного обращения к API нет.
2. Авторизация фиктивна: роль выбирается пользователем в `<select>` и пишется в
   `localStorage`. В реальном API роль приходит в ответе `POST /api/auth/login`
   и зашита в JWT. Селект роли — убрать категорически, это дыра в логике
   интерфейса: клиент не должен «выбирать, кто он».
3. Разметка прав в макете **инвертирована к API**: класс `hide-for-operator`
   прячет кнопки «Сохранить»/«Редактировать» от `operator`, хотя по API именно
   оператор (и админ) создаёт и редактирует, а читать без изменений может
   `engineer`. Всю роль-логику в макетах нужно перевернуть.
4. Ключевые экраны отсутствуют целиком: реестр инцидентов (в `incidents.html`
   есть только форма создания), карточка/редактирование инцидента, карточка
   аномалии с действиями, форма создания пользователя, все состояния
   (загрузка/пусто/ошибка/нет прав/сессия истекла), пагинация, мобильная версия.
5. Часть нарисованного бэкенд не умеет: карта сот на «Мониторинге», карточка
   «Доступность сети 99.2%» на дашборде, статусы и «последний вход» пользователей
   в админке, редактирование роли. Это раздел «Нет API» — нужен либо доработанный
   бэкенд, либо упрощение макета (решения расписаны в разделе 10).

### Что в макетах можно сохранить

- Тёмную тему и палитру (`#17171c`, `#26262e`, акцент `#e30613`), шрифт Segoe UI.
- Шапку с логотипом и вкладками разделов, карточную сетку KPI, таблицы, бейджи
  статусов/severity, ролевые бейджи, кнопки `.btn-primary/.btn-secondary/.btn-edit`.
- Трёхколоночный каркас «Мониторинга» (фильтры слева, область данных по центру,
  детали справа) — как каркас, с заменой содержимого.

| Блок ошибки | Над кнопкой, красная плашка | При 401: «Неверный логин или пароль»; при недоступности API: «Сервис недоступен, попробуйте позже» | **Нет в макете** |

## 4. Аварии / Инциденты (`incidents.html`)

Это самый недостроенный раздел: в макете есть **только форма создания**, а реестра,
карточки и редактирования нет совсем. При этом в `reports.html` дизайнер по сути
нарисовал реестр аварий — его надо перенести сюда, а отчётность переосмыслить
(раздел 6).

### 4.1. Реестр аварий `/incidents` (нет в макете — нужен полностью)

**Верх страницы — панель инструментов (одна карточка-тулбар):**

| Элемент | Где | Логика |
|---|---|---|
| Период `from`–`to` (datetime) | Слева в тулбаре | Обязателен для API; по умолчанию последние 30 суток; кнопка «Показать» |
| Поиск по PW/описанию/элементу | Рядом с периодом | Клиентская фильтрация по уже загруженному списку (в API поиска нет) |
| Фильтры: направление, ТЦ, категория, severity, «только открытые» | Вторая строка тулбара или сворачиваемая панель | Справочники — из `GET /api/reference/all`; фильтрация клиентская |
| Кнопка «+ Новая авария» | Справа в тулбаре | Только `operator`/`admin`; у `engineer` отсутствует |
| Кнопка «Выгрузить CSV» | Рядом | `GET /api/incidents/export?from&to`; доступна всем ролям |

**Таблица аварий (карточка под тулбаром):**

| Колонка | Поле API | Примечание |
|---|---|---|
| PW/NTT | `pw` | Клик → карточка инцидента |
| Направление | `directionCode` | |
| ТЦ | `techCenterCode` | |
| Приоритет | `priorityCode` | В макете отсутствует |
| Категория | `category` | Русская подпись из `/api/reference/all` |

### 4.2. Форма создания аварии `/incidents/new`

В макете форма есть, но покрывает примерно треть полей API и с неверными
справочниками. Нужно сгруппировать все поля `CreateIncidentRequest` в секции
(форма — отдельная страница или широкое модальное окно):

**Секция «Основное»:**

| Поле формы | Поле API | Тип элемента | Статус |

| Номер PW/NTT | `pw` | Текст, до 450 символов, счётчик/подсказка | Есть в макете |
| Сетевой элемент | `networkElementId` | **Выпадающий список с поиском**, не текстовое поле: подписи из справочных данных и карточек аномалий; при выборе `servElem` подставится из `full_name` на сервере | Доработать |
| Обслуживаемый элемент | `servElem` | Текст; подсказка «подставится из сетевого элемента, если он выбран» | **Нет в макете** |
| Кол-во БС | `numbRbs` | Текст | **Нет в макете** |

**Секция «Классификация» (все select'ы наполняются из `GET /api/reference/all`,
ничего не хардкодить, как сейчас СВН/ЕКБ/LTE):**

| Поле формы | Поле API | Статус |
|---|---|---|
| Направление | `directionId` | Есть элемент, значения заменить на справочник |
| ТЦ | `techCenterId` | Есть элемент, значения из справочника; список зависит от выбранного направления только если фронт решит фильтровать — API такой связи в справочнике не отдаёт, кроме `directionId` у ТЦ — можно фильтровать на клиенте |
| Приоритет | `priorityId` | **Нет в макете** |
| Тип сети | `networkTypeId` | Есть элемент, значения из справочника |
| Тип оборудования | `equipmentTypeId` | **Нет в макете** |
| Тип аварии | `alarmTypeId` | **Нет в макете** |
| Регион | `regionId` | **Нет в макете** |
| Категория | `category` | Доработать: в макете «1/2/3» — это неверно. Категория: Электроснабжение/Транспорт/Оборудование/ПО/Плановые/Клиент/Внешнее/Прочее |

### 4.3. Карточка инцидента `/incidents/:id` (нет в макете)

Открывается кликом по строке реестра, ссылке с дашборда или из аномалии.

**Шапка карточки:** `PW`/«Инцидент #id», бейдж severity, бейдж состояния
(Открыт/Завершён по `endTime`), кнопки «Изменить» и «Удалить» (только
`operator`/`admin`).

**Тело — те же 4 секции, что форма создания, но в режиме чтения** (сетка
«подпись — значение»): все поля детального объекта из раздела 6 API-документации,
включая `createdByUserId`/автора, `createdAt`, `updatedAt`, вычисленные
`lenght`/`commonProstoy`. Пустые значения показывать прочерком.

**Вкладка/блок «Связанные аномалии»** внизу карточки: таблица из
`GET /api/incidents/{id}/anomalies` — колонки: ID, соты (`cellId`, БС, сектор),
тип, KPI, severity, период, observed/expected, статус. Клик по строке → карточка
аномалии в мониторинге. Пустое состояние: «Этим инцидентом аномалии не объяснены».

**Редактирование** — та же форма, что создание (4.2), предзаполненная, с
предупреждением: «При сохранении незаполненные поля будут сброшены» (PUT —
полная замена). Кнопка «Сохранить изменения».

**Удаление** — только через модальное подтверждение: «Удалить аварию PW-…?
Связанные аномалии будут отвязаны и вернутся в статус “Новая”». Кнопки
«Отмена»/«Удалить» (красная). После успеха — тост и возврат в реестр.

## 5. Мониторинг (`monitoring.html`)

Сохранить каркас из трёх колонок: фильтры слева, центральная область, детали
справа. Содержимое требует переработки.

### 5.1. Что не так с текущим макетом

- Гекс-«карта» — декоративная: соты не привязаны ни к каким данным. В API нет
  координат сот и нет списка **всех** сот со статусами — есть только аномалии
  (`GET /api/anomalies`). Нарисовать честную карту по текущему API нельзя.
- Правая панель «Детали соты» показывает CSSR и DCR одновременно, но аномалия
  несёт один KPI (`kpiCode`, `observedValue`, `expectedValue`). Пары
  «CSSR+DCR по соте» API не отдаёт.

### 5.2. Решение для MVP: мониторинг = работа с аномалиями

Центральную область сделать таблицей/списком аномалий (карту оставить на будущее,
раздел 10). Элементы:

**Левая колонка «Фильтры» (сохраняется, значения — реальные):**

| Элемент | Параметр API | Статус |
|---|---|---|
| Период from–to | `from`, `to` (обязательны) | **Нет в макете** — добавить date/datetime |
| Регион | `regionId`, справочник из `/api/reference/all` | Есть элемент, значения из справочника |
| Статус аномалии | `status`: Новая/Подтверждена/Объяснена/Решена/Ложная | Доработать: в макете статусы «Аномалия/Предупреждение/Норма» — это не статусы, а уровни; заменить |
| Severity | `severity`: info/warning/critical | **Нет в макете** |
| Тип аномалии | `type`: threshold/zscore/missing_data/logical/cross_source | **Нет в макете** |
| KPI | `kpiCode` (текст/список: cssr, dcr, availability…) | **Нет в макете** |
| БС | `btsId` | **Нет в макете** |
| Кнопка «Сбросить» | Сброс всех фильтров к периоду по умолчанию | **Нет в макете** |
| Легенда цветов | Соответствие: critical — красный, warning — оранжевый, info — синий/серый | Есть в макете (смысл поправить) |

**Центральная область — таблица аномалий** (`GET /api/anomalies`, пагинация
`page`/`pageSize` под таблицей):

Колонки: ID, время (`tsFrom`), БС (`btsCode` + `btsFullName`), сектор, регион,
тип, KPI, факт (`observedValue`), ожидание (`expectedValue`), `score`,
severity-бейдж, статус-бейдж, связанный инцидент (`incidentPw`, если есть).
Клик по строке выбирает аномалию в правой панели. Счётчик «Всего: N» — из `total`.

**Правая колонка «Детали аномалии» (переосмысление «Деталей соты»):**

| Элемент | Данные |
|---|---|
| Заголовок | «Аномалия #id», бейджи severity и статуса |
| Соты/БС | `btsCode`, `btsFullName`, сектор, регион, `cellId` |
| Период | `tsFrom` — `tsTo`, `detectedAt` |
| KPI-блок | Название `kpiCode`, `observedValue` крупно (цвет по severity), рядом `expectedValue` и отклонение/`score` |
| Связанный инцидент | Если `incidentId` задан: карточка-ссылка PW + категория → переход в `/incidents/:id`. Если нет: серая плашка «Не объяснена» |
| Действие «Объяснить инцидентом» | Только `operator`/`admin`. Открывает модалку: выбор инцидента (список/поиск по PW из `GET /api/incidents` за период) → `POST /api/anomalies/{id}/explain` |
| Действие «Сменить статус» | Только `operator`/`admin`. Выпадающий список статусов + «Сохранить» → `PATCH /api/anomalies/{id}/status`. Подсказка: статусы «Новая» и «Ложная» сбросят привязку к инциденту |
| Состояния | «Выберите аномалию в списке» до выбора; скелетон при загрузке |

### 5.3. Карта (будущее, не MVP)

Гексы/карту не удалять из дизайна как идею, но верстать её после появления
бэкенда (раздел 10): нужны все соты с координатами и текущим состоянием, а не
только аномалии. До этого момента карта вводит в заблуждение.

## 7. Админ-панель (`admin.html`)

Страница только для роли `admin`. Две карточки макета (пользователи и аудит)
лучше развести по вкладкам внутри раздела: «Пользователи» и «Журнал аудита»,
чтобы не скроллить две большие таблицы подряд.

### 7.1. Вкладка «Пользователи»

Источник: `GET /api/admin/users`.

| Элемент | Где | Статус |
|---|---|---|
| Таблица: Пользователь (`username`), Роль (бейдж), Создан (`createdAt`) | Основная карточка | Доработать: колонки «Статус» и «Последний вход» и кнопка «Изменить» в макете — **нет API**, убрать из MVP |
| Человеческие имена («Иванов И.И.») | — | Убрать: API знает только `username`; ФИО в системе нет |
| Кнопка «+ Создать пользователя» | В заголовке карточки справа | **Нет в макете** |
| Форма создания (модалка или отдельная карточка) | По кнопке | **Нет в макете**: поля `username` (до 64), `password` (минимум 4, с показом пароля), `role` (select: Инженер/Дежурный/Администратор). Ошибки: 400 с полем, 409 «пользователь существует» — подписью под полем логина. Успех — тост + новая строка в таблице |
| Действия над существующими пользователями | — | **Нет API и нет в макете по-настоящему**: смена роли, блокировка, удаление эндпоинтами не предусмотрены. В MVP колонки «Действия» нет. Если бизнесу нужна — это доработка бэкенда (раздел 10), а не дизайна |

### 7.2. Вкладка «Журнал аудита»

Источник: `GET /api/admin/audit`. В макете таблица есть, но без фильтров, пагинации
и половины полей API.

**Панель фильтров над таблицей** (все — **нет в макете**):

| Элемент | Параметр API |
|---|---|
| Период from–to | `from`, `to` |
| Пользователь | `userId` — select из списка пользователей (7.1) |
| Действие | `action` — select из справочника действий (таблица раздела 12 API-документации: Вход, Создание пользователя, Создание аварии и т.д.) |
| Кнопки «Показать» / «Сбросить» | — |

**Таблица:** Время (`ts`), Пользователь (`username`), Роль (бейдж), Действие
(русская подпись по справочнику + серым кодом), Объект (`entityType` + `entityId`,
кликабельно: инцидент → карточка, аномалия → мониторинг), IP (`ipAddress`),
Результат (`success`: зелёный «Успех» / красный «Ошибка» — в макете этого нет, а

**Детали записи:** раскрытие строки (или боковая панель) с полем `details`, если
оно заведено в схеме: для аномалий — было/стало, для выгрузок — период и
количество строк. В базовой схеме `details` может отсутствовать — тогда блок
просто не показывать.

## 10. Чего не хватает в API для нарисованного дизайна

Эти пункты дизайнер не решит — это развилки «доработать бэкенд или упростить
интерфейс». Рекомендации — в третьем столбце.

| # | Что нарисовано | Чего нет в API | Рекомендация |
|---|---|---|---|
| 1 | Карточка «Доступность сети 99.2%» | Нет эндпоинта KPI/доступности; `kpi_cell_hourly` наружу не отдаётся | MVP: заменить карточку на «Аномалий за период». Потом: `GET /api/monitoring/availability` |
| 2 | Карта сот (гексы) на Мониторинге | Нет всех сот с координатами и текущими статусами; аномалии не содержат lat/lon | MVP: таблица аномалий (раздел 5.2). Потом: `GET /api/monitoring/cells` (соте + статус + KPI) |
| 3 | «Детали соты» с CSSR и DCR одновременно | Аномалия несёт один KPI, пары по соте нет | Показывать KPI именно выбранной аномалии. Потом — тот же эндпоинт клеток |
| 4 | «Критичные: 2 на направлении СВН» | `reports/summary` не режет по направлениям | Убрать подпись или считать на клиенте по списку инцидентов |
| 5 | Фильтры «направление/критичность» в Отчётности | У `/api/reports/*` только `from`/`to` | Клиентская фильтрация детализации; для сводки фильтров нет |
| 6 | Пагинация в таблицах инцидентов | У `GET /api/incidents` пагинации нет | Клиентская нарезка; при росте данных — `page/pageSize` на бэкенде |
| 7 | Пользователи: статус, последний вход, ФИО, «Изменить» | У `GET /api/admin/users` только `username/role/createdAt`; эндпоинтов изменения роли/блокировки нет | MVP: только список + создание (7.1). «Последний вход» при желании собирать на клиенте из аудита (`action=login&userId=…`), но лучше отдельным полем/эндпоинтом |
| 8 | Статусы инцидента «Авария/В работе/Закрыта» | Поля статуса у инцидента нет | Выводить вычисляемое состояние по `endTime`: Открыт/Завершён |
| 9 | Предзаполненные логин/пароль и выбор роли на входе | Противоречит API и безопасности | Удалить, роль — только из ответа логина |

## 11. Приоритеты реализации интерфейса

**MVP (без этого приложение не работает):**

1. Реальный вход с JWT, хранение токена, роль из ответа, выход, перехват 401.
2. Каркас: шапка с именем/ролью, навигация по ролям, тосты, скелетоны, пустые
   состояния, экран 403.
3. Дашборд: 3 KPI без «доступности» (всего, открытые, критичные) + последние
   инциденты.
4. Аварии: реестр с периодом и фильтрами, создание (все поля), карточка,
   редактирование, удаление с подтверждением, связанные аномалии.
5. Мониторинг: таблица аномалий с фильтрами, панель деталей, «Объяснить» и
   «Сменить статус» (без карты).
6. Отчётность: период, сводка (total/категории/severity), обе CSV-выгрузки.
7. Админка: список и создание пользователей, аудит с фильтрами и пагинацией.

**Вторая очередь:**

- Диаграммы дашборда (категории, severity, динамика по дням).
- Таблица детализации в отчётности с клиентскими фильтрами.
- Раскрытие `details` в аудите, кликабельные объекты в журнале.
- Адаптивная вёрстка под планшеты/телефоны в полном объёме.

**После доработки бэкенда (раздел 10):**

- Карта сот и карточка доступности сети.
- Управление пользователями (роль, блокировка), «последний вход».
- Серверные фильтры/пагинация инцидентов и отчётов.
